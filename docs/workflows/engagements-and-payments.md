# Engagements, quotations, invoicing and payments

Implementation: `packages/finance/src` (`@simplexd/finance`, shared by the web app and the worker), routes under `apps/web/src/app/api/v1/{service-requests/[id]/(triage|assign|quotes|transitions/staff),quotes,invoices,payment-attempts,refunds,bank-transfer-receipts,credit-notes,receipts,finance,webhooks/paystack}`, worker handlers in `apps/worker/src/handlers/payments.ts`. Pure logic it builds on: `@simplexd/domain/workflow` (state machines), `@simplexd/domain/ledger` (postings, allocation planning — see [accounting.md](../providers/accounting.md)) and `@simplexd/integrations/payments` (provider adapter — see [paystack.md](../providers/paystack.md)). Build brief §8, §12, §16, §18, §19; acceptance scenarios 3 and 6.

## 1. Principles

- **Every change is a state-machine transition** (`engagementMachine`, `invoiceMachine`, `paymentAttemptMachine`, `refundMachine`) with an append-only log row, an audit entry and an outbox event in the same transaction.
- **Authorisation before privilege.** Callers pass a `FinanceActor` (authz actor + row-level-security context). Reads run under the caller's own context so they prove access; the package elevates to the system context only for privileged tables (journals, provider events, chargebacks, reconciliations, document sequences) after the decision was made. Customers of another organisation get `not_found`, never data.
- **Money is integer kobo (`bigint`)** from request to ledger. Clients send descriptions, quantities and unit amounts; the server recomputes line amounts, subtotals, tax (from `tax_treatments`) and totals.
- **Nothing settles on a promise.** A redirect, a webhook receipt, an uploaded transfer receipt or a submitted refund moves no money. Only a server-side verification whose status, reference, amount **and** currency match the attempt allocates funds.
- **One settlement path.** `settleAttempt` is the only function that allocates gateway money; the verify endpoint, the callback, the webhook job and the reconciliation job all end there. The allocation's unique `dedupe_key` (`payment_attempt:<id>`, `bank_receipt:<id>`, `credit_note:<id>`) and the journal's unique `business_event_ref` make replays and races harmless.
- **Secrets never leave the adapter.** Responses carry hosted-checkout URLs and access codes only; provider payloads are stored sanitised (`providerResponseSanitized`), raw webhook bodies are kept for signature re-verification but never logged.

## 2. Engagement flow

```
inquiry ─triage→ triage ─issue quote→ quoted ─accept→ accepted ─┬─ invoice issued → awaiting_payment ─verified payment→ in_progress
                                                                └─ no upfront payment ──────────────────────────────→ in_progress
```

| Step              | Who                                                                                                        | Endpoint                                                        | Effect                                                                                                                                                                                                                                                                                                               |
| ----------------- | ---------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Triage            | staff `service_requests.triage`                                                                            | `POST /service-requests/{id}/triage`                            | assigned PM, priority, `slaDueAt` from `sla_policies` (service-specific over global; business-hours policies approximated in calendar hours until the escalation calendar lands)                                                                                                                                     |
| Assign            | staff `service_requests.assign`                                                                            | `POST /service-requests/{id}/assign`                            | (re)assign; `startWork: true` on an accepted request starts work without upfront payment (recorded as `no_upfront_payment`)                                                                                                                                                                                          |
| Draft quote       | staff `quotes.issue`                                                                                       | `POST /service-requests/{id}/quotes`                            | from a `quote_templates` row or lines; percentage fees derive the line from `feeBasis.percentageBps × basisAmountKobo` and are stored on the version                                                                                                                                                                 |
| New version       | staff `quotes.issue`                                                                                       | `POST /quotes/{id}/versions`                                    | supersedes the current version; quote returns to draft until issued                                                                                                                                                                                                                                                  |
| Issue             | staff `quotes.issue`                                                                                       | `POST /quotes/{id}/issue`                                       | quote → issued (`validUntil`, default 14 days), engagement → quoted, `quote.issued` event; older issued quotes for the request become superseded                                                                                                                                                                     |
| Accept            | customer `org.quotes.accept`, **Idempotency-Key required**                                                 | `POST /quotes/{id}/accept`                                      | `acceptances` row (signature name, terms version, IP hash, user agent), quote → accepted, engagement → accepted; percentage fee basis copied to the request; then the deposit/service invoice is issued (engagement → awaiting_payment) or work starts (→ in_progress) when `requiresPayment=false` / `depositBps=0` |
| Reject            | customer or staff                                                                                          | `POST /quotes/{id}/reject`                                      | reason required; engagement → rejected (no billing)                                                                                                                                                                                                                                                                  |
| Staff transitions | staff (`triage` for reject, `override` for cancel/in_progress/deliver/complete, `assign` for pause/review) | `POST /service-requests/{id}/transitions/staff`                 | reason and `billingConsequence` recorded in the transition metadata; `void_unpaid_invoices` voids unpaid invoices with reversing journals, paid work is left for finance (`invoice_pro_rata` / `refund_per_policy`)                                                                                                  |
| Expiry            | job                                                                                                        | `payments.reconcile_pending` (also `engagements.expire_quotes`) | issued quotes past `validUntil` → expired; engagement stays quoted for re-issue                                                                                                                                                                                                                                      |

Customer transitions (cancel/pause/resume) remain in the intake module's `POST /service-requests/{id}/transitions`.

## 3. Invoices

- Created from a quote version (on acceptance), or manually by finance (`finance.invoices.manage`, step-up auth) for milestones, management fees and other kinds. Drafts carry a provisional `DRAFT-…` number.
- `issue` assigns `INV-YYYY-NNNN` from a per-year sequence (advisory lock inside the transaction) and posts `invoiceIssued` (`invoice:<id>:issued`) under the system context in the same transaction. Recognition policy is `on_issue` pending the accountant's review; deposits are always unearned (2000).
- Tax: `taxTreatmentKey` snapshots the treatment onto the invoice; `withholdingKobo` is the expected withholding (informational until the customer's evidence is recorded with `taxWithheld`). `total = subtotal + tax` always.
- Installment plans are JSON (`label`, `amountKobo`, `dueDate`) and must sum to the total; a payment attempt may pay one installment or the balance, nothing else.
- `void` needs a reason and no allocations; issued invoices get a reversing journal (`invoice:<id>:void`). Anything allocated is corrected with a credit note.
- Reads: customer `org.invoices.view`, staff `finance.read`; row-level security applies first.

## 4. Payment attempts and settlement (scenario 6)

1. `POST /invoices/{id}/payment-attempts` (customer `org.invoices.pay`, Idempotency-Key required) resolves the provider: the active Paystack configuration for the current environment (`loadIntegrationConfig`, secrets decrypted at call time), otherwise the labelled development adapter when `APP_ENV≠production`, otherwise `provider_not_configured`. The attempt row (`SXD-<12 hex>`, immutable amount = balance or a permitted installment, currency, environment) is committed **before** `initialize`, so a lost provider response can still be verified. On success the row moves to `pending` with `authorizationUrl`/`accessCode`.
2. The customer pays on the hosted checkout (or the dev page) and returns to `GET /payment-attempts/callback?reference=`; the customer portal can also call `POST /payment-attempts/{id}/verify`. Both call `provider.verify`, run `matchVerification` and apply the decision:
   - `settle` → `settleAttempt`: system context, one transaction: lock the attempt `FOR UPDATE`, stop if an allocation with `payment_attempt:<id>` exists, re-match against the locked record, check the environment, post `gatewayPaymentSettled`, insert the allocation, update the invoice through `planAllocation`/`invoiceMachine`, issue `RCT-YYYY-NNNN` once, store the sanitised provider response, move a waiting engagement to `in_progress`, append audit + `payment.settled` + `invoice.paid|partially_paid`.
   - `mismatch` (amount — even larger —, currency, reference, status conflict, environment) → attempt `uncertain`, reconciliation exception `verification_mismatch`, **never** allocated.
   - `fail` → `failed`/`abandoned`; `keep_pending` → `pending`; `mark_uncertain` (24 h without a final answer) → `uncertain` + exception; `reverse` → attempt `reversed`, settlement journal reversed (`payment_attempt:<id>:reversed`), exception for finance; `no_change` → nothing.
3. Webhook `POST /webhooks/paystack`: raw body bytes, HMAC-SHA512 with the configured secret (dev adapter secret locally), constant-time comparison. Invalid or missing signature → `provider_events` row with `signature_valid=false`, 401, no job. Valid → parse, `deriveDedupeKey`, insert (duplicates return 200 without a new job), enqueue `payments.process_provider_event` in the same transaction.
4. Worker `payments.process_provider_event`: re-parses the stored body, refuses events whose `domain` differs from the endpoint's environment (exception `environment_mismatch`), loads the current attempt/refund/chargeback state and runs `planWebhookActions`: `verify_and_settle` (verify + the same `settleAttempt`), `update_refund`, `open_chargeback`/`resolve_chargeback` (privileged tables + journals), `chargeback_reminder`, `flag_for_reconciliation`, `ignore` (replays, stale states).
5. `payments.reconcile_pending` (every 5 minutes): re-verifies `initialized`/`pending`/`uncertain` attempts older than 10 minutes with the same matcher, polls refunds in flight, expires quotes and keeps the day's `reconciliations` row (kind `payments`) with a summary and the exception list. Staff endpoints: `GET /finance/reconciliation/attempts`, `GET /finance/reconciliation/exceptions` (`finance.reconcile`), `GET /finance/exports/allocations.csv|json` (`finance.export`; one row per allocation with receipt number and journal debit/credit totals, so the ledger ties to the invoices).

Bank transfers: `POST /invoices/{id}/bank-transfer-receipts` (customer) declares a transfer — posts nothing. `POST /bank-transfer-receipts/{id}/confirm` (finance `finance.allocations.manage`, step-up auth) allocates the **confirmed** amount once (`bank_receipt:<id>`), posts `bankTransferConfirmed`, issues the receipt; `reject` records the note.

Credit notes: `POST /invoices/{id}/credit-notes` (finance) posts `creditNoteIssued`, applies `planCreditNoteApplication` through an allocation keyed `credit_note:<id>` and numbers it `CN-YYYY-NNNN`. Never a refund.

## 5. Refunds

`requested → approved → submitted → pending → settled | failed`, `requested → rejected`, `failed → approved` (retry).

- Request: finance `finance.refunds.request` or the paying organisation (`org.invoices.view`, creates the request for finance). Idempotency-Key required. Total requested can never exceed the payment.
- Approve: `finance.refunds.approve`, step-up authentication, **approver ≠ requester** (both the policy's own-work rule and an explicit check). Posts `refundApproved` (liability in 2200) and emits `refund.approved`, which the outbox routes to `payments.submit_refund`.
- Submit (worker): the idempotency key is stored on the refund before `createRefund`; a retry with a recorded provider id reconciles with `getRefund` instead of re-submitting. Submission alone never settles.
- Settle only when the provider reports `processed` (webhook `refund.processed` or poll): `refundSettled` (`Dr 2200 / Cr 1100`). `pending`/`processing` keep it pending; `needs-attention` keeps it pending and opens an exception; `failed` reverses the approval liability (`refund:<id>:failed`) and opens an exception. Out-of-order events are ignored as stale or flagged when they conflict. An uncertain refund never credits the customer.

## 6. Chargebacks

`charge.dispute.create` → `chargebacks` row, `chargebackOpened` journal, reconciliation task; `charge.dispute.remind` → exception with the evidence deadline; `charge.dispute.resolve` → `chargebackWon` (reversal) or `chargebackLost` (loss expense) only for unmistakable resolutions, otherwise finance confirms first. The original payment history is never edited.

## 7. Development adapter

`/dev/paystack-checkout?reference=…` renders only outside production, is labelled "Development adapter — not a real gateway", shows the attempt and offers **Simulate success / failure / abandon**, which drive `DevPaymentProvider.simulate` and redirect to the callback. The adapter keeps simulated transactions in memory **per process**: the web process (checkout, callback, webhook route) shares one instance; a separate worker process cannot verify a dev attempt and will record `provider status unknown` → `keep_pending`, so drive dev payments through the callback/verify endpoints. Paystack test mode is the sandbox for end-to-end worker journeys.

## 8. Events and jobs

Outbox events: `engagement.transitioned`, `quote.issued|accepted|expired`, `invoice.issued|paid|partially_paid|voided`, `payment.initialized|settled|reversed`, `bank_transfer.declared|rejected`, `refund.requested|approved|pending|settled|failed`, `credit_note.issued`, `chargeback.opened|won|lost`. Jobs: `payments.process_provider_event`, `payments.submit_refund`, `payments.reconcile_pending` (scheduled), `engagements.expire_quotes`, `finance.post_payment` (legacy no-op: posting happens at settlement).
