# ADR 0001: Platform architecture

Status: accepted (2026-09-23)

## Context

The build brief asks for a TypeScript modular monolith: Next.js App Router for the
public site, portals, admin and versioned API; a separate worker process; PostgreSQL
with PostGIS; Redis; a durable job queue; private S3-compatible storage; a maintained
authentication library with organisations, session control and MFA.

## Decisions

1. **pnpm workspace monorepo** with `apps/web`, `apps/worker`, `packages/domain`,
   `packages/db`, `packages/ui`, `packages/integrations`, `packages/contracts`,
   `data/`, `tests/`, `docs/`. Workspace packages are consumed as TypeScript source
   (`exports` point at `src/*.ts`); Next transpiles them, the worker is bundled with
   esbuild, tests run through Vitest.
2. **Next.js 16 App Router** (`apps/web`) serves every surface and the `/api/v1`
   route handlers on the Node runtime. Standalone output is used for containers.
3. **Drizzle ORM + node-postgres.** Schema lives in `packages/db/src/schema`, SQL
   migrations are generated by drizzle-kit and committed. Spatial operations use
   reviewed parameterised SQL through Drizzle's `sql` tag; PostGIS `geometry(Point,4326)`
   columns and GiST indexes are declared in the schema.
4. **Two database roles.** Migrations run as the schema owner (`MIGRATION_DATABASE_URL`).
   The application connects as `simplexd_app`, a non-superuser without `BYPASSRLS`,
   so row-level security policies on organisation-scoped tables are enforced.
   Every request-scoped database operation runs in a transaction that sets
   `app.user_id`, `app.org_id`, `app.staff` and `app.role` with `SET LOCAL`
   (`packages/db/src/tenant.ts`). Application policies remain the primary authorisation
   layer; RLS is defence in depth. The startup check warns loudly when the runtime
   role could bypass RLS.
5. **Authentication: better-auth** (email/password with scrypt, sessions with
   revocation, TOTP two-factor with backup codes, organisations with invitations,
   rate limiting). We do not implement password hashing or token cryptography.
   Authorisation is ours: `packages/domain/src/authz` evaluates permissions from staff
   roles, organisation membership roles, partner assignments and explicit resource
   grants, default deny.
6. **Durable jobs in PostgreSQL, Redis for ephemeral state.** The transactional outbox
   (`outbox_events`) and the job table (`jobs`) are written in the same transaction as
   the business change, then consumed by the worker with `FOR UPDATE SKIP LOCKED`,
   exponential backoff, bounded attempts and a dead-letter state with admin retry.
   Redis provides rate limiting, short-lived caches and coordination locks. This
   satisfies "durable job queue" with fewer moving parts than a Redis-backed queue and
   removes the two-phase commit problem between the database and the queue. It is
   documented here as an equivalent maintained approach.
7. **Money is integer kobo** (`bigint`), serialised as decimal strings in JSON. The
   ledger is a balanced double-entry journal with append-only posted entries;
   corrections are reversals.
8. **Provider adapters behind interfaces** (`PaymentProvider`, `SmsProvider`,
   `MailProvider`, `CalendarProvider`, `StorageProvider`, `MalwareScanner`). Each has a
   labelled development adapter that is only selectable when `APP_ENV=development`
   or `APP_ENV=test`. Production refuses to start with a development adapter.
9. **Secrets** are envelope-encrypted with AES-256-GCM under a master key supplied by
   the environment (`SECRETS_MASTER_KEY`) or a KMS-backed key reference. Secret fields
   are write-only in the API; only masked presence and rotation metadata are readable.
10. **UI**: Tailwind CSS v4 with design tokens as CSS custom properties, Radix UI
    primitives for accessible headless behaviour, react-hook-form + zod for forms,
    TanStack Table for data tables, Recharts for charts, MapLibre GL JS for the map,
    CSS transitions with `prefers-reduced-motion` and an in-app reduce-motion setting.

## Consequences

- One deployable unit for the web app and one for the worker, both containerised;
  Compose files provided for any Docker-capable server.
- Tests can run against a real PostgreSQL/PostGIS instance, including RLS checks.
- Some brief items depend on external accounts (Paystack, Termii, SMTP, Google, map
  tiles, S3). They are implemented against official documentation and exercised with
  contract fixtures and development adapters; live sandbox verification is tracked in
  `IMPLEMENTATION-STATUS.md`.
